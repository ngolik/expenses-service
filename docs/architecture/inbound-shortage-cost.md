# Architecture: Record a shortage amount tied to a delivery

## 1. Scope and constraints

- **Problem**: `expenses-service` has no way to record a mandatory shortage money amount tied to a delivery id and an identified operator, distinct from the shipped `waiting-delivery-cost` and `damaged-inbound-writeoff` amounts for the same delivery. The existing `POST /expenses/rest/add` accepts any `Expense` with an optional `UserID` and no delivery concept at all; neither the `waiting-cost` nor `damage-writeoff` path has a discriminator that would tell a future shortage record apart from a wait-cost or damage-writeoff record sharing the same `DeliveryID`.
- **Goals**: A new, additional creation path that requires all three of delivery id, an identified (auth-service-validated) operator, and an amount — reject if any is missing/invalid (spec AC2, AC3, AC4) — and marks the resulting record as a shortage so it stays distinguishable from a wait-cost or damage-writeoff record for the same delivery (spec AC1, Repos §`expenses-service`, resolves the spec's Open question 3). A new read-by-id path returning delivery id, user id, and amount (spec AC7).
- **Non-goals**: The warehouse-facing "mark delivery as short + optional remark" half (owned by `arrival-service`, out of this repo — spec `## Repos` `arrival-service` paragraph). No remark/text field here — the spec's optional ≤500-char remark (AC5, AC6) lives on `arrival-service`'s `Arrival.shortRemark`, not on this repo's `Expense`. No list-all endpoint for shortage records (spec AC8, Out of scope). No live call to `arrival-service` to confirm the delivery id exists — presence of the id is enough, matching the `waiting-delivery-cost`/`damaged-inbound-writeoff` precedent. No change to `POST /expenses/rest/add`, `GET /expenses/rest/all`, or any `waiting-cost*`/`damage-writeoff*` route/behavior.
- **Constraints**: Go 1.18, Gin, GORM, Postgres — same stack as `waiting-delivery-cost`/`damaged-inbound-writeoff`, confirmed from `go.mod`/`database/config.go`. No new external dependency added — the existing `authclient.HTTPUserValidator` is reused as-is. No new test dependency added — reuses the existing fake-repository/fake-validator pattern.
- **Sources used**: `docs/specifications/inbound-shortage-cost.md` (scratch-ai-skills-pilot, read-only reference — the cross-repo contract memo already resolves the AC1 mechanism as a new `Expense.IsShortage` field, reusing the `UserValidator`/`ExpenseRepository`/`ValidationError`/`UpstreamError` types, and the two new routes); this repo's `model/expense.go`, `service/waiting_delivery_cost.go`, `service/damage_writeoff.go`, `api/waiting_delivery_cost.go`, `api/damage_writeoff.go`, `api/api.go`, `authclient/client.go` (all reused/extended, not reimplemented); `docs/architecture/waiting-delivery-cost.md` and `docs/architecture/damaged-inbound-writeoff.md` (style/structure precedent for this doc).

## 2. Existing shape to respect

- `api.SetupRoutes` groups everything under `/expenses/rest` and already wires six handlers: `AddExpenseHandler`/`GetExpensesHandler` (unvalidated, untouched), `AddWaitingDeliveryCostHandler`/`GetWaitingDeliveryCostHandler`, and `AddDamageWriteOffHandler`/`GetDamageWriteOffHandler` (both validated, both untouched).
- `model.Expense` already carries `DeliveryID int` (added for `waiting-delivery-cost`) and `IsDamageWriteOff bool` (added for `damaged-inbound-writeoff`), plus the original `UserID`/`Amount`. This story reuses `DeliveryID`/`UserID`/`Amount` rather than duplicating them — the spec's `expenses-service` paragraph decided a discriminator field, not a second set of fields, mirroring the `IsDamageWriteOff` precedent.
- `service/waiting_delivery_cost.go` already defines the `UserValidator`/`ExpenseRepository` interfaces, the `ValidationError`/`UpstreamError` types (with `newValidationError`/`newUpstreamError` helpers), and `DefaultExpenseRepository` (GORM-backed). All of these are reused as-is by this story — no redefinition, no duplication (same reuse `damage_writeoff.go` already established).
- `database.MigrateDatabase()` runs `DB.AutoMigrate(&model.Expense{})` on every startup — the new `IsShortage` column is picked up automatically, no manual migration step needed, same as `DeliveryID` and `IsDamageWriteOff` were.
- `authclient.HTTPUserValidator` (auth-service client) has no changes to make — it is reused exactly as `waiting-delivery-cost`/`damaged-inbound-writeoff` wired it.

## 3. Recommended change

| Component | Responsibility | Notes |
| --- | --- | --- |
| `model.Expense` | Add `IsShortage bool` field | Reuses the existing `Expense`/`expenses` table and its `DeliveryID`/`UserID`/`Amount` fields. Zero value (`false`) is what every existing record — plain `/add`, wait-cost, and damage-writeoff records — already has, so this is a backward-compatible additive column. Only `service.AddShortage` sets it `true`. |
| `service` (new file `shortage.go`) | Business rules for the new path | Reuses the existing `UserValidator`/`ExpenseRepository` interfaces and `ValidationError`/`UpstreamError` types from `waiting_delivery_cost.go` — no redefinition. `AddShortage` validates delivery id / user id / amount presence, calls the validator, sets `IsShortage = true`, then persists via the repository. `GetShortage` reads by id via the repository. `AddWaitingDeliveryCost`/`GetWaitingDeliveryCost` and `AddDamageWriteOff`/`GetDamageWriteOff` are untouched. |
| `api` (new file `shortage.go`) | New HTTP surface | `AddShortageHandler` (`POST /expenses/rest/shortage`) and `GetShortageHandler` (`GET /expenses/rest/shortage/:id`), mirroring the siblings' structure exactly: package-level `shortageValidator`/`shortageRepo` vars wired to the real `authclient.HTTPUserValidator`/`service.DefaultExpenseRepository` in production, swappable in tests. Same error-to-status mapping (400 validation, 502 upstream, 500 other, 404 not-found, 400 non-numeric id). |
| `api.SetupRoutes` | Route registration | Adds the two new routes under the existing `/expenses/rest` group; all six existing routes are unchanged (same path, same handler, same order). |
| `database` | Migration | No code change — `AutoMigrate(&model.Expense{})` already covers the new `IsShortage` column. |

- Happy path (create): handler binds JSON → `service.AddShortage` checks delivery id / user id / amount are non-zero → calls `UserValidator.UserExists(userID)` → on `true`, sets `IsShortage = true` and persists via `ExpenseRepository.Create` → 200 with `{id, deliveryId, userId, amount}` (the generated `id` included, same pointer-parameter reasoning as `AddWaitingDeliveryCost`/`AddDamageWriteOff`, so the caller can retrieve the record afterwards — spec AC7).
- Validation failure (missing delivery id/user id/amount — spec AC2/AC3/AC4 — or auth-service reports the user id doesn't exist): `service.ValidationError` → handler returns 400.
- Auth-service unreachable / unexpected response: `service.UpstreamError` → handler returns 502.
- Persistence failure (DB error after all validation passed): plain `error` → handler returns 500.
- Read: handler parses `:id` → `service.GetShortage` → 404 if not found (`gorm.ErrRecordNotFound`), 500 for any other DB error, 200 with `{id, deliveryId, userId, amount}` otherwise (spec AC7). `IsShortage` is not exposed in the response body — it is a storage-level discriminator, not part of the finance-facing read shape (mirrors both siblings' response shape).

## 4. Key decisions and risks

| Decision | Options considered | Choice | Rationale |
| --- | --- | --- | --- |
| AC1 discriminator mechanism | New table/model vs. a discriminator field on the existing `Expense`/table | New field (`IsShortage bool`), reusing `DeliveryID`/`UserID`/`Amount` | Already resolved by the specification's `## Repos` `expenses-service` paragraph before this implementation started (resolves Open question 3). A shortage record and a wait-cost/damage-writeoff record are structurally identical (delivery id + validated user + amount); a boolean flag is sufficient to keep them business-distinguishable without duplicating fields or introducing a second table — same pattern `IsDamageWriteOff` already established. |
| Interface/error-type reuse | Redefine `UserValidator`/`ExpenseRepository`/`ValidationError`/`UpstreamError` in the new file vs. reuse the siblings' | Reuse as-is from `service/waiting_delivery_cost.go` | All three paths share identical validation shape and persistence needs; redefining would either collide (same package, same names) or fork behavior for no reason. Reusing keeps `AddShortage`, `AddDamageWriteOff`, and `AddWaitingDeliveryCost` provably consistent in how they treat validation and errors — resolves the spec's Open question 1 (identity check reuses the existing pattern, no new check). |
| Remark field | Add a remark field on `Expense` for this path vs. leave it entirely to `arrival-service` | Leave it to `arrival-service` | The spec's optional ≤500-char remark (AC5, AC6) is explicitly attached to the warehouse-facing fact in `## Repos` `arrival-service` paragraph (`shortRemark` on `Arrival`), not to the finance-facing amount. Adding a duplicate remark field here would create two sources of truth for the same text with no consumer for the `expenses-service` copy. |
| Response body shape | Expose `isShortage` in `ShortageResponse` vs. omit it | Omit | The route itself (`/shortage` vs `/waiting-cost`/`/damage-writeoff`) and the response type (`ShortageResponse`) already tell the caller which kind of record it's looking at; exposing the internal flag adds no information the caller doesn't already have from which endpoint it called — same choice `damaged-inbound-writeoff` made. |
| Test doubles for persistence | GORM against sqlite in-memory vs. reusing the siblings' fake `ExpenseRepository`/`UserValidator` | Reuse `fakeExpenseRepository`/`fakeUserValidator` (service package) and `waitingCostFakeRepo`/`fakeValidator` (api package) | Same rationale as `waiting-delivery-cost`/`damaged-inbound-writeoff`: no new dependency, and reusing the exact same fakes lets a shortage-vs-siblings distinguishability test create all three record kinds in one shared fake repository instance. |

## 5. Implementation handoff

- Touch areas: `model/expense.go` (add field), `service/shortage.go` (new), `api/shortage.go` (new), `api/api.go` (register two routes). No change to `authclient/client.go`, `service/waiting_delivery_cost.go`, `service/damage_writeoff.go`, `api/waiting_delivery_cost.go`, `api/damage_writeoff.go`, `api/expense.go`, `service/expense.go`, or `database/config.go`.
- Tests: `service/shortage_test.go`, `api/shortage_test.go` — table-driven where the shape fits, reusing the siblings' fakes and `setupRouterForTest`/`performRequest` helpers. Includes a dedicated distinguishability test at both the service and handler level: create a wait-cost record, a damage-writeoff record, and a shortage record for the same `DeliveryID` in the same fake repository, then fetch all three back and assert `IsShortage` correctly distinguishes the shortage record (spec AC1).
- Config surface: none added — reuses `AUTH_SERVICE_BASE_URL` (already present for `waiting-delivery-cost`/`damaged-inbound-writeoff`).
- Branch: `feature/SCRUM-5-inbound-shortage-cost` (already checked out, cut from `main`).
